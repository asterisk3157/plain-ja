# README とドキュメント

README、導入方法、使い方、設定のページに当てる決まりです。共通の決まり(SKILL.md の1〜10)に加えて当てます。

## 中身

1. **最初の1文**:「〇〇は〜です」で、何に使うものかを言います。作りの説明(データベースです)や、誤解を招く言い方(AI 内包の〜)にしません。
2. **前提は書かない**:一般的な操作の説明、手順に要らない理由、念のための注記は書きません。(例:--help の説明、「ターミナルを開いたままにしてください」、エラーが出る仕組みの説明、「最初の公開」)
3. **説明してから使う**:まだ説明していない言葉を、先に見出しや本文に出しません。
4. **値の出どころを書く**:ユーザーが自分で用意する値は、どこから取るかを書きます。(例:「環境変数に設定します」→「初期設定のコマンドが作ったファイルの中身を、環境変数に設定します」)
5. **確かめ方を書く**:手順の後に、うまくいったかの見分け方を1つ書きます。
6. **例を付ける**:設定や入力は、そのまま使える形の例を付けます。例の値は1つにそろえます(例:公開 URL は https://app.example.com)。スクリーンショットは迷いやすい画面だけにし、テスト用のデータで撮ります。
7. **コマンドと設定は AI に任せる**:コマンド、設定、ツールの名前は、人ではなく AI エージェントが読みます。人向けのページでは表に並べず、必要なときだけ本文に1つ書くか、設定のページへリンクします。

## 形

8. **見出しは名詞で**:手順の見出しは「〜の作成」「〜の起動」の形にそろえます。折りたたみの見出しは、開く前に中身が分かる名前にします。(例:はじめかた → 導入方法、データフォルダを作る → データフォルダの作成)
9. **ページの役割を分ける**:導入方法はセットアップだけにします。使い方、連携の例などは別のページにします。
10. **読み手で分ける**:読み手の立場が違うとき(1台で使う、ホストする、クライアントとして使う など)は、最初に選ぶ表を置き、立場ごとの節へ飛ばします。
11. **表にするもの**:条件、機能、オプション、時刻のように、項目と値が並ぶものは表にします。版は「v… 以上」で書きます。
12. **補足は折りたたむ**:本文には手順に要ることだけを置き、詳細や困ったときの対処は折りたたみ(`<details>`)に入れます。
13. **OS・ツールごとに分ける**:OS ごとの違いは「macOS・Linux の場合:」のような見出しで分けます。ツールごとの手順は、色の印を付けた枠(🟧 Claude Code、⬛ Codex など)にします。
14. **リンクは一覧**:ほかのページへの入口は、文にせず「名前:リンク」の一覧にします。
15. **決まっていないところは準備中**:中身が決まっていない節は、推測で書かず「準備中です。」とだけ書きます。

## README

16. **並び順**:1文の説明 → 主な機能 → インストール方法 → うまく動かないときは… → ドキュメント → バージョン履歴 → ライセンス。前提や注意(v0.1 なので〜など)は入れません。
17. **機能の表**:「機能」と「説明」の2列にします。各行は何ができるかを書き、手段や物の名前(Web UI、AI エージェント)を機能にしません。重なるものはまとめ、問いが違うもの(何をやるか、いつやるか)は分けます。説明は1行にします。
18. **図と画像**:良い図が浮かぶまでは入れません。npm などで表示が崩れる形(Mermaid、GitHub のコールアウト)は使いません。バッジと折りたたみは使えます。
19. **履歴**:版ごとに1行にし、詳細はリリースのページへ「詳細はこちら」でつなぎます。
